The short version

Your browser encrypts each file with AES-256-GCM before upload.
We store ciphertext and never receive the key.
Everything after # is the key.
Browsers don't send it to any server, including ours.

We delete the ciphertext from our disk within a minute of its exit.
If the exit was a download, we wait for it to finish (at most ).
We keep a note that the link existed, so we can tell you why it's gone.
We never had the key, so any leftover bytes are noise.

Every exit goes on the public record: we add it to SealLog on the Ootle at the next checkpoint (within ).
It proves we said we deleted it, publicly and permanently.
It can't prove we kept no copy.

Your key is the account

No email, no password.
Your key is the account.
Keep it like a house key: lose it and nobody, including us, can let you back in.

We store a random id and a hash of your login key.
No email and no public key; a drop link stores its own address, by design.

Make my drive makes the key in this browser at once.
Save it as a key file, locked with a passphrase if you like, and Open my drive takes it back on any device.
Your drive's Tari keys come from the same key, the first time a Tari feature needs them.

The locks

  • Files: AES-256-GCM in your browser, in chunks; size padded so the exact size stays hidden.
  • Names: file and folder names are locked too.
    Search runs in this browser.
    Our server can't read your file names.
  • The key: in the link after #, or sealed to a Tari address inside a stealth payment's encrypted memo.
  • Secret words: stretched in your browser with PBKDF2, rounds; we slow down guessing after wrong tries.
  • Photos: location and camera data removed before locking, unless you keep the original.
The cryptography, in full

Everything that touches a file or a key runs in your browser, with your browser's own WebCrypto.
The server never receives a file key, a link's secret, a password or your seed.
At sign-in it sees your login key and keeps only its SHA-256.

  • Files: a fresh random 32-byte key per file.
    The content is padded with Padmé (at least 1 KB, at most 12% over above that), cut into 4 MB chunks and encrypted with AES-256-GCM.
    Each chunk's nonce holds its index and a “last chunk” flag, and every chunk authenticates the file's header, so reordering, truncation and extension all fail.
  • Metadata: the name, type and real size are encrypted separately, also with AES-256-GCM, padded to a multiple of 256 bytes.
  • Keys from keys: HKDF-SHA256 with a separate label for every purpose, so one derived key reveals nothing about another.
  • Links: every link has its own 32-byte secret, after the #.
    It unwraps the file key and derives an access token; our server stores only the SHA-256 of that token.
  • Passwords: PBKDF2-SHA256, rounds, combined with the link's secret by default (link + password), so a copy of our database isn't enough to guess it.
  • Your drive: one 32-byte seed made in your browser, kept in its storage, and backed up as your key file (locked with a passphrase if you choose) or written down.
    Everything else is derived from it: the login key (we store its SHA-256), the drive's Tari keys (made only when a Tari feature first needs them), a separate wallet key, and the dead-drop tags.
    There is no email and no password with us.
  • Folders: every folder has its own random key.
    A file's key is wrapped under its folder's key, and a folder's under its parent's, up to your drive's root key.
    A folder link carries one folder key, so it opens what is below that folder and nothing above it.
  • Safety code: 12 emoji (96 bits) derived from a Tari address's public keys, so two people can compare an address out loud.
  • Proof of work: SHA-256 with a number of leading zero bits, instead of a captcha.
    Your browser solves it in a background worker.
  • Photos: location and camera data are removed from JPEG, PNG and WebP files before encryption, unless you choose to keep the original.

Sealing a file to a Tari address

When you send a file to a Tari address, your browser seals the link's secret to that address's two public keys, the owner key and the view key, using the official Tari library for the key agreement.
The sealed blob is 125 bytes, and it travels as the memo of a stealth payment.

  • Why a view key can't open your files: the seal needs both the owner key and the view key to open.
    A view key alone shows that a delivery arrived, its amount and its memo text, but not the file.
  • The exception, labelled: a sender can choose “The recipient uses another Ootle wallet”.
    That seal uses the view key only, so anyone with that view key can open the file, and the send screen says so.
  • Who posts the payment: our relay.
    We post the payment for you, so we learn the address you send to, never the key.
    The server writes the memo from its own address; a client supplies only the sealed blob.
  • Who posts the payment: your browser, once its wallet holds the testnet grant our sponsor wallet sends when a drive opens: it builds, signs and pays for it, and our server passes it to the network without learning who it's for.
    Until the grant arrives (a minute or two), our relay posts the send and learns the address while it's sent.
    A browser send spends that grant, so the chain links your sends to the sponsor wallet and to each other.
    Dead-drop deliveries still go through our relay, because a drop's address is public by design.

Folders and their keys

Folders are a tree of keys.
Each file's key is locked under its folder's key, so one folder link opens the files below it and nothing above.

Our server sees which files share a folder, how deep it goes and how many files are in it.
Never a name.

A folder link counts visits, not files.
A Once folder link is one visit of ; then the link ends.

Moving a file into a folder that has a link shares it too, and the drive says so before it moves.

Pay to open

Pay to open is built and switched off on this deployment.
Until it is on, this is how it will work.

The money goes straight to the owner's Tari address; our server keeps half of the key and hands it to the buyer once Tari's chain shows the payment, so the owner can be offline and we never hold the money or the whole key.

Next: the locked payment, a Tari payment with a refund built in, so a buyer gets the money back if the owner never delivers.
It isn't built yet.

The split key, and its limits
  • We keep half of the key and give it to you once the chain shows your payment.
    The other half is in the link, which we never see.
    Neither half opens it alone.
  • If the link leaks, our server could open it too.
  • Our half of a paid link's key stays in our database backups for after the link ends.
  • We check the amount and that the payment is on the chain.
    Only the owner's drive can check the money is theirs to spend.
  • Test money comes from our demo wallet, so it can be grouped with our other payments.
    It opens at once, because our wallet built it.
    Paid from your own wallet?
    It opens after the owner's drive checks it.
  • Payments can't be taken back, by us or by Tari.
    Pay only if what you see here is enough.
  • To see who paid you, we keep your sales view key.
    It is sealed, so a copy of our database can't read it.
    Our payment checker on our server can.
    A view key can see payments, never spend them.

Our server, in detail

Sees and stores
Ciphertext and its padded size; the hour an item arrived and when it left; expiry and view counts, and the time of a link's first open (shown only to its owner); the exit rule (link or password); for drives: a random-looking drive id, a hash of its login key, the first and last active day, how many distinct days it was active, quota and packs bought; for folders: which items share a folder and how many levels down it sits, never a name; per link, how many times it opened in each hour; whether a file is in the trash, and when it is set to leave; invoices (pack, amount, status) and the chain outputs that paid them; drop links: the drop's Tari address, its label, its tag and daily counters; abuse reports; notes about ended links (state and day).
Sees, never stores
Every uploader's and every opener's IP address, live (so at the moment it happens we could link who uploaded a link with who opened it); the login key at sign-in; access tokens (hashed on arrival); which drop a file was left in, and the submitter's IP; the destination Tari address of every send, the sealed 125-byte blob, which drive sent it, and by timing which link it carries, kept in the job until sent and then scrubbed; that your drive submitted a transaction, not to whom; for dead-drop deliveries, the drop's address while the delivery is sent.
Never sees
File names, types, contents and real sizes; file keys, link secrets, passwords, seeds or any private key; your drive's Tari address, unless you make a drop or a relay send goes to it; who you send a file to, when your browser's wallet sends it (until its grant arrives, our relay sends it and learns the address while it's sent); which chain outputs your browser can open (everyone downloads the same copy of the chain); who shares with whom (a link is the only way a file leaves your drive, and we never learn who holds it).

Free space, and when files go

How we decide: every hour we take the disk, set aside what the system needs, what people have rented and a share for uploads without a drive, and divide the rest among drives used in the last .
We overbook like an airline (×): most people use a fraction of their share.
The number moves slowly, never below or above .

If the disk ever truly fills, new uploads pause for everyone, and nothing already stored is lost.

When the number goes down, nothing of yours is deleted.
You can't add more until you're under it again.

Files shared without a drive have their own reserved space, and small files (up to ) have a reserved lane of their own, so a busy day of big uploads can't crowd out a quick note.

If you don't open your drive for days, we delete what's in it.

When extra space ends, nothing goes for days.

How SealLog works

SealLog is a template on the Ootle.
At each checkpoint, at most apart, we add one Merkle root over the ciphertext hash of every file we stored and a record of every exit.
The log in use is the one /api/v1/config names.

  • What a proof shows: that the tree we committed to at that epoch contains your file's ciphertext hash, or the record of its exit.
    Not that we held the bytes, and not that we deleted them.
  • What nobody can change: the log has no owner, so nobody, us included, can change its rules or the code behind it.
    Anyone can check owner_rule: "None" in its header on an indexer.
    Checkpoints are only ever added.
  • Who writes it: one key, our service key, the same one that holds our public tTARI.
    It can add any root, stop, or start a new log.
    Nothing yet proves that each checkpoint extends the last one.
  • What it shows everyone: a rough upper bound on how many records (stored files plus exits) we've written, in steps of 64; for each checkpoint window, how many whole multiples of 64 records arrived (usually none); and the writer key.
  • The code it runs: anyone can check that the template on the chain is our published seal_log.wasm, byte for byte, with template/check.sh --onchain and the template's address.

Pages allow scripts, styles, fonts and requests only from this origin, and nothing inline is allowed to run.

      What we can't hide
      
      
      Beyond what our server sees (who sees what), here is what we can't protect you from:
      
        
        
    
      1. The person you send it to. 
        They can save, screenshot or forward it.
        2. 
    
      2. Anyone who gets the full link. 
        The link is the key. 
        Add a secret word (sent another way) or send it to one Tari address.
        3. 
    
      3. Chat apps that preview links. 
        Their servers see the full link. 
        They can't use up a view (opening takes a click), but they could open it.
        4. 
    
      4. Your own browser. 
        Your browser history, and any history sync, can keep the full link, key included. 
        We clear the key from the address bar once it's opened, but we can't reach your history. 
        Extensions allowed to read your tabs can see the link. 
        Clipboard history (and cloud clipboards) can keep a copied link.
        5. 
    
      5. A compromised device or extension. 
        Encryption in the browser can't beat malware in the browser.
        6. 
    
      6. A malicious version of this website. 
        It's the known weak spot of all web encryption: if our server were compromised, it could serve code that leaks keys. 
        SRI only pins files to this page; it can't protect you from us. 
        What can: our verify-deploy script and running your own copy.
        7. 
    
      7. Metadata. 
        We see a padded size (rounded up so the exact size stays hidden: at least 1 KB, and at most 12% over for anything bigger), the hour it arrived, when it leaves (rounded up to the hour when that's an hour or more away; “midnight” is your own local midnight, which shows your time zone), its exit rule and how often it's opened. 
        Not the name, the type, the contents or the key. 
        Our server sees your IP address while you're connected. 
        We don't write it to disk: rate limits use a keyed hash, kept in memory, with a key that changes every day. 
        A VPN or Tor hides your IP from us; links without a drive work in Tor Browser's Safer mode, and Tari features need WebAssembly.
        8. 
    
      8. On-chain facts. 
        The chain shows an output with a hidden amount, a hidden owner and an encrypted memo. 
        The fee is public. 
        Payments our relay sends all come from one wallet with the same fee, so someone watching could group them as “sent by {{BRAND}}”, but not see to whom. 
        Sends from your browser spend a grant from our sponsor wallet, then each send's change, so anyone reading the Ootle can link them to each other and to our sponsor wallet, but not see to whom or how much.         
        SealLog shows roughly how many records (stored files plus exits) we write, in steps of 64, and when.
        9. 
    
      9. Deletion you can't see. 
        We delete on cue, and nothing can prove we kept no copy. 
        Disks can't be securely wiped, so deleted ciphertext can linger in free blocks. 
        Without the key it's noise. 
        Our host also takes automatic snapshots of the whole server and keeps them for a few weeks. 
        A file that existed when one was taken stays in it, as ciphertext, until that snapshot is rotated out.
        10. 
    
      10. Testnet resets. 
        Esmeralda can be reset. 
        Payments and on-chain records from before a reset are archived in our repository; files on our server are not affected.
        11. 
    
      11. Legal requests. 
        If compelled, we can hand over what we have: ciphertext, the columns “What our server knows” prints, invoices. 
        Not contents. 
        Not keys.
        12. 
  
      
      
      
      
      
        
      What never touches a disk
      
        
      
          
      Our server and web server never write your IP address, your links or your files' ids to a log. 
      The database holds file and link ids, never keys; Privacy lists every table.
      
  
        
    
      • Web server: no access log, and the error log drops addresses, paths, hosts and headers.
        • 
    
      • API: logs only the route's name, the status and how long it took.
        • 
    
      • Rate limits: a keyed hash of your network prefix, kept in memory, with a key that changes every day.
        • 
    
      • Background jobs: fixed codes, never addresses, ids or memos. 
        Our own test transactions are the only ones we publish.
        • 
    
      • The firewall: logging is off. 
        System journal: kept for seven days.
        • 
  
      
  
      That's not the same as “nobody ever sees your IP”: our server sees it while you're connected, and so could our host.
      
        
      
      
      
      
      
    
      

    
      
      
      How it was built, and tested
      
      
      No analytics, no trackers, no third-party scripts or fonts. 
      Your browser contacts a Tari-run indexer only when you press “Check it on Tari's indexer”.
      
      
      Built with AI coding agents under the author's direction. 
      The design, threat model and crypto choices were reviewed by the author. 
      Python's standard library on the server, plain JavaScript in the browser. 
      One runtime dependency: Tari's official ootle-wasm , pinned by its sha512.
      
      
      Every release runs the server, site, browser and end-to-end test suites first; the records are in the repository. 
      This deployment runs commit {{GIT_SHA}}.
