Cryptography

Everything that touches a file or a key runs in your browser, with your browser's own WebCrypto. The server never receives a file key, a link's secret, a password or your seed. At sign-in it sees your login key and keeps only its SHA-256.

  • Files: a fresh random 32-byte key per file. The content is padded with Padmé (at least 1 KB, at most 12% over above that), cut into 4 MB chunks and encrypted with AES-256-GCM. Each chunk's nonce holds its index and a “last chunk” flag, and every chunk authenticates the file's header, so reordering, truncation and extension all fail.
  • Metadata: the name, type and real size are encrypted separately, also with AES-256-GCM, padded to a multiple of 256 bytes.
  • Keys from keys: HKDF-SHA256 with a separate label for every purpose, so one derived key reveals nothing about another.
  • Links: every link has its own 32-byte secret, after the #. It unwraps the file key and derives an access token; our server stores only the SHA-256 of that token.
  • Passwords: PBKDF2-SHA256, rounds, combined with the link's secret by default (link + password), so a copy of our database isn't enough to guess it.
  • Lockers: one 32-byte seed made in your browser, kept in its storage, and backed up as your recovery code or key file. Everything else is derived from it: the login key (we store its SHA-256), the locker's Tari keys, a separate wallet key, and the dead-drop tags. There is no email and no password with us.
  • Safety code: 12 emoji (96 bits) derived from a locker's public keys, so two people can compare a locker out loud.
  • Proof of work: SHA-256 with a number of leading zero bits, instead of a captcha. Your browser solves it in a background worker.
  • Photos: location and camera data are removed from JPEG, PNG and WebP files before encryption, unless you choose to keep the original.

Sealing a file to a Tari address

When you send a file to a Tari address, your browser seals the link's secret to that address's two public keys, the owner key and the view key, using the official Tari library for the key agreement. The sealed blob is 125 bytes, and it travels as the memo of a stealth payment.

  • Why a view key can't open your files: the seal needs both the owner key and the view key to open. A view key alone shows that a delivery arrived, its amount and its memo text, but not the file.
  • The exception, labelled: a sender can choose “The recipient uses another Ootle wallet”. That seal uses the view key only, so anyone with that view key can open the file, and the send screen says so.
  • Who posts the payment: our relay. We post the payment for you, so we learn the address you send to, never the key. The server writes the memo from its own address; a client supplies only the sealed blob.
  • Who posts the payment: your browser, once its wallet holds the testnet grant our sponsor wallet sends when a locker opens: it builds, signs and pays for it, and our server passes it to the network without learning who it's for. Until the grant arrives (a minute or two), our relay posts the send and learns the address while it's sent. A browser send spends that grant, so the chain links your sends to the sponsor wallet and to each other. Dead-drop deliveries still go through our relay, because a drop's address is public by design.

How payments are checked

In September a wallet bug on the testnet showed deposits that never happened (forum thread). A wallet saying “sent” isn't enough, so mutis credits rented space only after its own checks.

We credit a payment only after the official Tari library opens its commitment to the exact amount and a Tari-run public indexer shows it committed on the chain. The check runs in a separate process that can only read; walletd never decides a credit.

We credit a payment only after our wallet sees it and a Tari-run public indexer confirms it exists on the chain. The amount is the one our wallet reads; this deployment doesn't prove it with the official Tari library.

SealLog, our public record

SealLog is a template on the Ootle. At each checkpoint, at most apart, we add one Merkle root over the ciphertext hash of every file we stored and a record of every exit. The log in use is the one /api/v1/config names.

  • What a proof shows: that the tree we committed to at that epoch contains your file's ciphertext hash, or the record of its exit. Not that we held the bytes, and not that we deleted them.
  • What nobody can change: the log has no owner, so nobody, us included, can change its rules or the code behind it. Anyone can check owner_rule: "None" in its header on an indexer. Checkpoints are only ever added.
  • Who writes it: one key, our service key, the same one that holds our public tTARI. It can add any root, stop, or start a new log. Nothing yet proves that each checkpoint extends the last one.
  • What it shows everyone: a rough upper bound on how many records (stored files plus exits) we've written, in steps of 64; for each checkpoint window, how many whole multiples of 64 records arrived (usually none); and the writer key.
  • The code it runs: anyone can check that the template on the chain is our published seal_log.wasm, byte for byte, with template/check.sh --onchain and the template's address.

What never touches a disk

Our server and web server never write your IP address, your links or your files' ids to a log. The database holds file and link ids, never keys; Privacy lists every table.

  • Web server: no access log, and the error log drops addresses, paths, hosts and headers.
  • API: logs only the route's name, the status and how long it took.
  • Rate limits: a keyed hash of your network prefix, kept in memory, with a key that changes every day.
  • Background jobs: fixed codes, never addresses, ids or memos. Our own test transactions are the only ones we publish.
  • The firewall: logging is off. System journal: kept for seven days.

That's not the same as “nobody ever sees your IP”: our server sees it while you're connected, and so could our host.

Headers and content security policy

Every response carries HSTS, X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, Cross-Origin-Opener-Policy and Cross-Origin-Resource-Policy: same-origin, X-Frame-Options: DENY and a Permissions-Policy that turns off the camera, microphone, location, payment and USB APIs.

Pages allow scripts, styles, fonts and requests only from this origin, and nothing inline is allowed to run. The app pages add WebAssembly for the official Tari library, Trusted Types where the browser supports them, and the two Tari-run indexers for the “Check it on Tari's indexer” button.

Verify this deployment

SRI only pins files to this page; it can't protect you from us. What can: comparing what we serve with the published source, release hashes notarized on the Ootle, and running your own copy.

  1. Every build writes a manifest with the SHA-256 of every file this site serves and the git commit it came from.
  2. tools/verify-deploy.py rebuilds the site from a clean checkout of that commit, downloads every file in the live manifest, and prints any difference.
  3. Since SealLog went on, each release's manifest hash is also notarized through it; /releases.json lists them with their transactions. Anyone can notarize, so only events whose signer is the log's writer key are ours.
$ git clone {{REPO_URL}}
$ cd mutis
$ python3 tools/verify-deploy.py {{ORIGIN}} {{GIT_SHA}}

It needs git and Python 3.11 or newer. This checks the site now. A browser can't pin it for you between visits.

Check it in your devtools

No analytics, no trackers, no third-party scripts or fonts. Your browser contacts a Tari-run indexer only when you press “Check it on Tari's indexer”. To see it for yourself:

  1. Open your browser's developer tools and choose the Network tab.
  2. Reload this page, then drop a file on the home page.
  3. Every request goes to this site's own address. Nothing else appears unless you press “Check it on Tari's indexer”.
