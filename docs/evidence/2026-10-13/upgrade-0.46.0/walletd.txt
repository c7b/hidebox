== Why the sponsor stays stuck (walletd 0.46.0 source at the tag, cc8a83bc)
  The sponsor's whole balance is commitment 3ee453abdd3dd93b…, the change of its 10:39 send
  2749858a…. It is on chain: both indexers answer GET /substates/utxo_…_3ee453ab… 200 (a Utxo
  substate, version 0, 18:27), and mutis's mirror has it (chain_utxos seq 1463, epoch 12214,
  first seen 10:39:32). walletd holds it as LockedUnconfirmed, is_on_chain false, under the lock of
  2749858a…, which stays Pending:
  1. crates/wallet/sdk/src/apis/transaction.rs:233-243: a 404 for the result is "Transaction result
     not found … Will check again later" and the transaction stays Pending, with the comment
     "TODO: if this happens forever we might want to resubmit or mark as invalid".
  2. The indexer's 404 is final: applications/tari_indexer/src/transaction_manager/mod.rs:179-262
     asks the transaction's committee first and answers NotFound when the committee has no result
     (it no longer keeps one for transactions older than about an epoch or two: #156 from 16:58 was
     already 404 at 18:14).
  3. crates/wallet/storage_sqlite/src/writer.rs:2497-2517 locks_release_stale: "A lock linked to a
     transaction is released when that transaction resolves, never by timeout", so the lock of
     2749858a… is never reaped.
  4. crates/wallet/sdk/src/apis/stealth_outputs.rs:626-645 upsert_utxo: when the scanner finds an
     output the wallet already holds, its status changes only if it is Unspent ("If not unspent, don't
     allow status to be changed"); verify_and_update_outputs (same file, 685-) touches only is_burnt
     and is_frozen of a known output. So the UTXO scanner can't turn 3ee453ab… back into Unspent.
  5. There is no RPC or CLI to settle, cancel or rescan (release-notes.txt, last section). The two
     ways to drop a lock both delete the change: writer.rs:132-163 stealth_outputs_release_by_lock_id
     ("Remove stealth_outputs that were created by this lock": LockedUnconfirmed rows are deleted), and
     a Rejected result does the same (transaction.rs:247-258). Resubmitting 2749858a… would abort on
     its spent input and take that path. `reset` wipes the wallet's local state.
  So walletd 0.46.0 has no documented way to re-derive this output from chain state, and the store is
  not edited by hand. Stopped here for the sponsor (README.md, "What remains for the owner").
