Two migrations, both additive (release-notes.txt): lock_owner adds a nullable column to `locks`,
trusted_validator_sets adds a table. The same accounts and balances as the live wallet read a
moment later. Under the full production sandbox walletd 0.47.0 started, migrated, answered RPC and
logged only what a network-less copy should (it can't reach an indexer, so it has no trusted
validator set yet): no EPERM, no denied path, nothing about the sandbox. So no directive of
walletd.service needed loosening.

The copy holds keys, and the script's exit trap is meant to delete it on every path. It didn't this
time: the trap ran `systemctl stop` (07:17:58) and then `systemctl reset-failed`, which an extra line of
this run's script added; on a transient unit that stopped cleanly that command fails ("not loaded"),
and under `set -e` a failing command inside the trap ends the trap, so `rm -rf` never ran. (The script
had reached the trap early: a `journalctl | head` pipe ended by SIGPIPE under pipefail, after every
check above had printed.) The copy was deleted by hand at 07:18:21, 23 s after the unit stopped
("drill copy removed: /var/lib/walletd-drill no longer exists"); it never left the 0700 directory.
The drill's own trap has the same weakness when `systemctl stop` itself fails (a unit that never
started), so upgrade-drill.md §3 now writes the trap as `systemctl stop walletd-drill 2>/dev/null || true;
rm -rf "$T"`.
